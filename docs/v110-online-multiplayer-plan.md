# ICE WOLF v1.1.0 Phase 2 — オンライン対戦（Supabase Realtime）設計メモ

Phase 1（6ステージ・衣装・10人戦・2人狼・観戦カメラ）が入ったので、Phase 2 は
**同じゲームを、離れた人と一緒に遊ぶ**ための設計です。ここでは「何を作るか」「どう
繋ぐか」「どの順で入れるか」だけを決めます。

> **実装済み（2026-11-18）**: §7 の1〜4（部屋とpresence、入力とスナップショット、
> スイッチ・ゲート・勝敗の同期データ、スタンプと観戦の受け口）を `v1.1.0 オンライン中核`
> / `オンラインロビー` / `クイックスタンプ` の3ブロックとして入れました。§3 のテーブルは
> 使っていません（Broadcast + Presence だけ。§3 は Phase 3 の履歴用に保留）。
> つなぎ方は `docs/v110-online-setup.md`、検証は `tests/pro/v110-online.test.mjs`。
>
> **Phase 2b 完了（同日）**: 最後に残っていた「リモートの位置を3Dに反映する」を
> `v1.1.0 オンライン対戦同期` として入れました。ゲストは CPU ブロックを止めて
> スナップショットで9席を動かし（5Hzを約110msで補間）、自分の席は入力で予測して
> 0.2秒ごとに32%だけ補正します。スイッチの配置・点灯・ゲート・タイマー・生存数・
> 勝敗もホストの値です（検証は `tests/pro/v110-sync.test.mjs`）。
> 外部の Supabase プロジェクトの URL / anon key を入れる以外に、通信対戦を
> 止めているものはありません。

## 0. Phase 1 がすでに用意しているもの

| Phase 2 が必要とするもの | Phase 1 の持ち物 |
| --- | --- |
| ステージの選択と配布 | `StageId` / `StageApplied`（6種、`classic` と `aquarium` は無料） |
| 人数と役割の配り方 | `PlayerCount`（7〜10）/ `WolfCount`（1〜2）/ `RosterIds`（YOU, A〜I） |
| 誰を観ているか | `SpectatorActive` / `SpectatorTargetId`（観戦カメラはそのまま流用） |
| 12言語 | 178キーの表（`__iceWolfI18n.t()`）と HUD の自動翻訳 |
| 課金の判定 | `ProUnlocked`（StoreKit 2 の権利。端末ごと） |
| 盤面の再現性 | 壁・スイッチ・ゲート・階段がすべて `game.json` のデータで決まる |

つまり Phase 2 で新しく作るのは **通信と部屋**だけで、ゲームの規則は1行も作り直しません。

## 1. 部屋（ルーム）

```
ホスト（1人）                        参加者（1〜9人）
  部屋を作る                            合言葉 or 招待リンクで入る
  人数 7..10 を選ぶ                     「準備OK」
  ステージを選ぶ                        ホストの開始を待つ
  開始 → 全員に同じ席・同じ役・同じ壁    自分の操作だけを送る
```

- 合言葉は6文字（英数字、紛らわしい 0/O/1/I を除く）。招待リンクは
  `icewolf://room/ABC123`（ユニバーサルリンクは Phase 2 の後半）。
- 席は **ホストが開始時に確定**します。`RosterIds` の並び（YOU, A〜I）に、
  参加者を入室順で割り当てます。以降、途中参加はできません（観戦のみ、§6）。
- 人数はホストが 7〜10 で選び、**ホストの Pro** が10人戦の鍵です。ホストが
  Pro でなければ 9人までに丸めます（Phase 1 の `iceWolfClampPlayerCount` をそのまま使う）。

### ステージの扱い（共有ステージと Pro ステージ）

| ステージ | 誰が選べるか | 参加者に必要か |
| --- | --- | --- |
| クラシック・アイスアリーナ | 全員 | 不要 |
| 深海水族館 | 全員 | 不要（**共有ステージ**。無料ユーザーも一緒に遊べる） |
| 霧の遊園地 / 雪山ロッジ / 廃校 / 宇宙船 | **ホストが Pro のときだけ** | 不要（絵は全員のアプリに入っている） |

理由: 4つの Pro ステージは「見た目と壁の配置」だけで、当たり判定や規則は共通です。
ホストが Pro なら部屋全体がそのステージで遊べる、という方が、10人集める実用性が
高く、審査でも「買った人の部屋に招待された人が遊べる」と説明できます。ホストが
Pro を失った（返金）場合は、次の試合から水族館に戻します（Phase 1 の
`resolvedId()` と同じ規則）。

## 2. 通信の形（ホスト権威）

ゲームの計算は**ホストの端末だけ**が行います。Phase 1 のブロックはそのまま
`roundPhase` を持っているので、クライアントは「自分の入力」と「自分が見ている
画面」だけを扱えば足ります。

```
クライアント                    ホスト
  入力 (10Hz)  ──────────────▶  移動・凍結・救助・スイッチ・勝敗を計算
                                （Phase 1 のイベントシートをそのまま実行）
  スナップショット (5Hz) ◀──────  全員の位置・状態・役割・HUD・タイマー
```

- **入力**: `{seq, moveX, moveY, action: none|wolf|rescue|switch, stamp}`。
  自分のキャラクターの移動は、なめらかさのためクライアントでも予測します
  （サーバーの権威はホスト。ズレたら 200ms で補間）。
- **スナップショット**: `{t, players:[{id, x, y, z, role, state, mode}], switches, gates, timer, phase}`。
  1人あたり約90バイト、10人で 5Hz なら 4.5KB/s。
- **乱数**: 役・スイッチ・ゲートの抽選はホストだけが引き、結果を配ります
  （クライアントの `Math.random` は使いません。Phase 1 の `makeLayout()` は
  ホストでだけ走らせ、`SwitchLayout` / `GateLayout` を配る形にします）。

## 3. Supabase の持ち物

```
rooms(id, code, host_id, stage_id, player_count, wolf_count, switch_count,
      status, created_at, started_at)
room_players(room_id, seat, display_name, client_id, ready, joined_at, last_seen)
room_events(id, room_id, seq, kind, payload jsonb, created_at)   -- 監査・再接続用
```

- Realtime は `rooms:{id}` のチャンネルに `broadcast`（入力・スナップショット）と
  `presence`（入室・退室・ハートビート）。
- `room_events` は最後の10件だけ残し、**再接続したクライアントに最新スナップショット**
  を渡すためだけに使います（リプレイ機能は Phase 3）。
- RLS: 参加者は自分の `room_players` 行だけ更新可。`rooms` の `stage_id` 等は
  ホストだけ更新可。`anon` キーはアプリに埋め込み、**書き込みは RLS で部屋単位に
  閉じる**（他の部屋を覗けない）。
- 認証: アカウントは作りません。端末ごとの `client_id`（アプリが作る UUID）だけ。
  表示名は「プレイヤー1〜10」+ 任意のニックネーム（12言語の既定名）。

## 4. 時計と切断

- 開始時にホストが `startAt`（サーバー時刻 + 3秒）を配り、全員が同じカウントダウンで始めます。
- 参加者が切れたら 30秒待ち、`presence` が戻れば同じ席に復帰（スナップショットを1枚もらう）。
  30秒を過ぎたらその席は「Out」（Phase 1 の待避と同じ扱い）にします。
- **ホストが切れたら** 残りのうち席の若い人へホストを移し、`room_events` の最後の
  スナップショットから再開します（`host_migration` イベント）。
- 試合中の途中参加はできません。観戦（§6）だけ受け付けます。

> **Phase 2c で決まったこと（実装済み）**: 計画では `room_events` の最後の
> スナップショットから再開する予定でしたが、Phase 2 はサーバーに保存しないため、
> 引き継いだ端末が**その端末の最後のスナップショット状態をそのまま正**として続けます。
> 12秒たってもスナップショットが来ない／次の席が無いときは、試合を終了して
> ONLINE 画面に戻します（`iceWolfOnlineHostCheck`、`docs/v110-online-setup.md` §7.2）。

## 5. 12言語のワンタップ・クイックスタンプ

文字チャットは作りません（モデレーション・審査・翻訳のコストを持たないため）。
代わりに**押すだけの定型スタンプ8種**を、全員の言語で表示します。

| キー | 日本語の例 | 用途 |
| --- | --- | --- |
| `stamp.hello` | よろしく！ | 開始前 |
| `stamp.nice` | ナイス！ | 凍結・救助成功 |
| `stamp.wait` | 待って！ | スイッチ前 |
| `stamp.help` | 助けて！ | 凍結された |
| `stamp.wolf` | あいつだ！ | 疑い（人狼だと決めつけない） |
| `stamp.thanks` | ありがとう | 救助された |
| `stamp.gg` | いい試合！ | 結果画面 |
| `stamp.sorry` | ごめん！ | 誤操作 |

- 送るのは**キーだけ**（`{kind:'stamp', key:'stamp.help'}`）。受けた側が自分の言語で
  表示します。だから翻訳の追加は表に1行足すだけで、通信は変わりません。
- クールダウン 2秒、1試合 30回まで。スタンプは音とアイコンだけで、位置情報などは
  一切送りません。

## 6. 観戦（Phase 1 のカメラをそのまま）

Phase 1 の観戦カメラは「凍結された自分」ではなく「他人」を追えるので、Phase 2 では
**凍結された参加者**がそのままこれを使います（`SpectatorActive`）。入室だけして
遊ばない人は `spectator` 席として、ホストのスナップショットを同じ形で受け取ります。

## 7. 実装の順番（各段階で受け入れ条件つき）

1. **部屋と presence（通信なしのゲーム）**: 部屋を作る・入る・準備・開始。
   開始したら全員が同じ `StageId` / `RosterIds` / `WolfCount` でローカルに対戦を
   始める（相手の動きは見えない）。受け入れ: 2台で同じ席・同じ壁・同じ役になる。
2. **入力とスナップショット**: ホスト権威の移動と凍結。受け入れ: 10人・5Hz で
   20ms 以内のジッタ、200ms の遅延でも破綻しない。
3. **スイッチ・ゲート・勝敗の同期**: `SwitchLayout` / `GateLayout` を配る。
   受け入れ: 二人同時押しでも1回だけ起動、ゲート開放が全員同じ。
4. **スタンプと観戦**: 8種のスタンプ、凍結者の観戦、ホスト移行。
   受け入れ: 言語を変えても同じスタンプが自分の言語で出る。

## 8. 審査・プライバシー上の注意

- ガイドライン1.2（ユーザー生成コンテンツ）: 自由入力のチャットを持たないこと、
  定型スタンプのみであることを申請メモに明記します。ニックネームは12言語の
  既定名を初期値にし、自由入力は任意（不適切語はクライアント側でブロック）。
- 収集するのは `client_id`（端末内生成）、表示名、対戦の結果のみ。位置情報・
  連絡先・Apple ID は取りません。プライバシーポリシー（`docs/PRIVACY.md`）に
  「オンライン対戦時は合言葉と表示名、対戦イベントを Supabase に保存する」を追記。
- オフライン（機内モード）でも Phase 1 の6ステージが全部遊べること。通信は
  「部屋に入ったとき」だけ使います。
